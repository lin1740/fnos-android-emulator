【付费说明】本应用自身免费。内置的云手机画面服务来自上游开源项目 ScrcpyOverWebRTC，其「授权管理」为第三方付费授权：免费版即可使用云手机画面、ADB 调试、文件推送等全部基础功能，仅"可添加的设备数量"受限；购买授权后仅增加可添加的设备数量，功能本身没有任何区别。相关付费与飞牛（fnOS）官方无关，费用由上游授权服务方收取。

【网络与端口】应用支持通过飞牛统一网关访问（应用中心点开即为 /app/androidemu），也支持局域网直连画面服务端口（8443/TCP）。为支持外网与手机 APP 直连，画面与调试端口（8443/TCP、3478/TCP+UDP、5556/TCP）可由使用者自行映射到公网，应用侧不做任何自动端口映射（无 UPnP/打洞）。各端口均有独立鉴权：画面服务需账号登录（默认账号 admin，首次登录后请立即修改默认口令）、ADB 默认仅监听本机须在面板手动开放、TURN 需要凭据。请自行评估公网暴露风险。

权限说明

本文档随应用分发包提供，向应用商店审核人员与本机使用者说明本应用的权限模型与
特权使用依据。

一、结论
1. 本应用不申请宿主 root：应用以专用包用户运行（config/privilege：run-as=package，
   用户 docker-androidemu，属组 docker），不存在以宿主 root 常驻的进程或服务；
   自 v3.6.5 起，gateway.py、audio_fix.py 等后台进程通过 _drop_privileges() 自动
   降权到 docker-androidemu 用户，进一步确保无 root 进程。
   容器编排由 fnOS Docker（docker-project 机制）以常规 compose 方式执行。
2. 整包仅一个容器以 Docker privileged（特权）模式运行：安卓主容器
   androidemu-android（redroid / Android 12）。容器内 root 是 Android 系统自身
   初始化所必需，不等于宿主 root。
3. 其余组件均以普通权限运行：云手机画面服务容器 androidemu-webrtc 无 privileged；
   应用界面（飞牛统一网关入口 /app/androidemu）与后台脚本只操作本应用自己的容器、镜像与数据卷。

二、为什么安卓主容器需要 privileged
1. redroid 是在 Docker 中运行 Android 用户态的上游方案（remote-android/redroid-doc），
   官方部署方式即要求 --privileged：Android 依赖内核 binder 通信，容器需要挂载/访问
   内核 binder（binderfs）设备并创建 binder 设备节点，这类操作需要完整设备访问与
   挂载能力，普通容器权限无法完成。
2. 更窄的替代方案已实测不可行：非特权 + device_cgroup_rule + 挂载 binderfs +
   cap-add=ALL + seccomp=unconfined —— 本应用 v1.0.30 实测容器以 ExitCode 0 静默
   退出、无法进入 Android 启动流程，故自 v1.0.31 起恢复 privileged；redroid 官方
   仓库对应诉求见 https://github.com/remote-android/redroid-doc/issues/591
   （Running redroid without privileged，至今仍为开放议题），可随时复现验证。
3. 运行前提：宿主内核须具备 binder 支持（无纯软件替代方案）：
   - x86 设备：通常安装 fnOS 应用中心提供的 binder_linux 驱动后产生 /dev/binder；
   - ARM 设备：多数设备内核已内置 binder/binderfs（可能无 /dev/binder 静态节点，
     由 privileged 容器内部自行挂载 binderfs）。
   自 2.0.0 起 manifest 不再硬声明 install_dep_apps=binder_linux_driver（避免 ARM 设备
   因依赖应用不匹配而无法安装），改为安装脚本自动实测检测（兼容 /dev/binder、
   binder_linux、binderfs 挂载、内核注册、模块加载五种形态），不满足时明确报错并
   中止安装，属功能前提而非提权手段。

三、权限影响面控制（已落地）
1. 应用本体：run-as=package，无 join-groups 附加系统组；Docker socket 访问能力来自
   privilege 声明的属组（docker 组，fnOS 标准机制），仅用于应用脚本对本应用容器的
   编排与清理。v3.6.5 起 gateway.py/audio_fix.py 自动降权到 docker-androidemu。
2. 容器面：privileged 仅存在于 redroid 一个服务；webrtc 无 privileged；compose 默认
   声明 devices（/dev/dri、/dev/binder）以明确最小设备透出面，安装/升级脚本会按宿主
   实际条件自动裁剪——宿主无 /dev/dri 时移除 /dev/dri 直通，
   宿主无 /dev/binder 静态节点（内核内置 binderfs，常见于 ARM）时移除 /dev/binder 直通，
   避免设备节点不存在导致容器创建失败。
3. 数据与文件：安卓数据存于专用数据卷 androidemu-data（容器重建/升级不丢失）；
   宿主仅以只读方式挂载 DRI 驱动目录（:ro，路径按宿主架构 x86_64/aarch64/armhf 自动探测）；
   不挂载任何宿主用户目录；卸载按向导选择保留或删除数据卷。
4. 网络：仅发布服务所需端口（ADB 5556、云手机画面 8443、TURN 3478 TCP/UDP、
   50000-50100/UDP 媒体中继），无额外暴露面。其中 ADB 5556 由宿主脚本
   redroid_adb_forward.sh 用 socat 监听 0.0.0.0:5556 并转发到安卓容器 adb 端口：
   原因是 fnOS 的 Docker 在当前内核下无法让宿主自身通过局域网 IP 回环访问已发布端口，
   导致「局域网 IP:5556」从 NAS 本机/容器内连接必然超时。
   该转发进程由应用安装/升级/启用时启动、卸载时结束。另：云手机画面服务（androidemu-webrtc）
   使用 host 网络命名空间（仍未使用 privileged）：fnOS 会拦截「bridge 容器 →
   宿主局域网 IP」，bridge 模式下云手机后台用 <局域网IP>:5556 添加本机设备会超时；
   host 网络下 <局域网IP> 与 127.0.0.1 的端口都能直连。监听端口与原先映射完全一致。
5. GPU 权限处理：默认使用软件渲染（gpu_mode=guest）保证稳定开机；x86 设备且检测到
   /dev/dri 时可由安装脚本自动切换为 GPU 直通（gpu_mode=host）。仅在 GPU 直通模式下
   对实际存在的 DRM 节点（card*/renderD* 通配）执行 chmod（容器内 Android 降权渲染进程
   需打开设备），设备缺失自动跳过并回退软件渲染（swiftshader）；容器启动后
   fix_gpu_perms.sh 幂等兜底（容器未运行或无 /dev/dri 时直接退出），不会触碰宿主机
   其它设备或资源。
5.1 宿主 DRM 节点放权（全程不需要宿主 root）：
   宿主 udev 每次开机会把 /dev/dri/card*、renderD* 置为 660 root:video|render，而容器内
   Android 的降权渲染进程（surfaceflinger/graphics）以普通身份打不开设备，结果是
   surfaceflinger 反复报 "no suitable EGLConfig found" 崩溃、Android 永远到不了
   sys.boot_completed=1、adbd 停在 USB 模式（容器内不监听 5555），表现为「adb 连不上 /
   device offline / 画面黑屏」。
   实现方式（实测有效，且不新增任何权限声明）：
   （a）scripts/gpu_release.sh（主路径，启动容器之前执行）：用本应用自己的穿云投屏
        webrtc 镜像（busybox 提供 /bin/sh）起一个 `docker run --rm` 临时容器，绑定挂载
        -v /dev/dri:/dev/dri 与宿主共享同一 inode，在容器内以 root 执行 chmod 666 ——
        实测宿主节点随即变为 666；之后才创建安卓容器，容器内节点即为 666，surfaceflinger
        首次启动即可成功。该临时容器用完即删、不常驻、不需要 --privileged、不需要宿主
        root；无 /dev/dri（软件渲染）或节点已为 666 时直接跳过。
   （b）scripts/fix_gpu_perms.sh（兜底，容器启动之后执行）：调用同一放权机制处理宿主
        节点，并按 surfaceflinger 的 PID 变化次数判定是否真的陷入崩溃循环；确认崩溃
        循环才 `docker restart` 本应用自己的容器，正常但较慢的首次启动不会被误打断。
   （c）两条路径都会把放权前后的真实权限与结论写入应用数据目录的 gpu_fix.log。
   管理员若希望开机即由 udev 置 0666，可用 sudo 执行
   <应用目录>/scripts/gpu_udev_rules.sh install 自行安装该规则（仅作用于 card[0-9]*、
   renderD[0-9]* 两类节点），卸载时同理用 sudo 手动删除。除上述 DRM 节点外，本应用
   不写入、不修改宿主机的任何其它设备、目录或服务。
6. 生命周期：安装/升级/卸载脚本幂等、输出重定向到日志；卸载默认清理本应用容器、
   网络与仅本应用下载的两个镜像，不影响其它应用；升级不删除用户数据卷与镜像缓存。
   v3.6.0 起安装/更新中断时自动清理临时数据，避免占位导致后续无法安装；
   v3.6.6 起重写 uninstall_init 升级守卫，修复"无法更新-执行脚本出错且原因未知"问题。

四、给审核/维护者的说明
- 需要复现 privileged 的必要性时：在装有 binder_linux 驱动的 fnOS 设备安装本包，
  将 compose 中 redroid 的 privileged 移除或改为 cap-add 方案，即可复现「容器以
   ExitCode 0 静默退出、无法开机」。
- 上游依据：redroid-doc 部署文档与 issue #591（见上）。
- 若平台后续更新容器运行规范、提供更窄的等效能力（如受控设备直通/绑定挂载支持），
  作者承诺在后续版本即时收敛特权面。

附、账号安全与权限口径
1. 账号安全：云手机画面管理后台默认账号 admin、默认密码 admin123；首次登录后请务必
   立即修改默认密码，并避免在公网直接暴露画面服务端口。未及时修改默认口令造成的
   风险由使用者自行承担。
2. 权限口径（可直接用于审核沟通）：
   - 本应用无任何宿主 root 常驻进程（v3.6.5 起后台进程自动降权）；
   - 全包仅 redroid（安卓主容器）一个容器需要 privileged，系上游技术必需（见本文档
     第二节与第三节），已随 compose 注释、应用介绍、《免责声明》多处声明；
   - 「容器内部以 root 运行」≠「特权容器」≠「宿主 root」：webrtc 等普通容器即便
     内部进程为 root，也仅在该容器命名空间内，不具任何宿主能力；
   - 应用脚本以非 root 专用账号（run-as=package）运行；其 Docker socket 编排
     能力来自 fnOS privilege 机制声明的 docker 属组，用于本应用自身容器的编排与清理。

   飞牛侧仍需登录飞牛 OS 才能访问网关入口。
